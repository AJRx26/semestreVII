¡Claro! No tengo acceso a tus máquinas virtuales, así que aquí tienes una guía para resolver el examen paso a paso. Si me pegas las salidas de los comandos, te ayudo a interpretarlas y a redactar los hallazgos.

## 1. Diagnóstico inicial (antes de modificar nada)

Guarda captura o salida de cada comando, con fecha, y escribe una línea de interpretación por evidencia.

**Usuarios y privilegios**
```bash
awk -F: '$3==0 {print $1}' /etc/passwd          # ¿otros UID 0?
awk -F: '$3>=1000 {print $1,$3,$7}' /etc/passwd  # usuarios reales
getent group sudo; getent group wheel
sudo grep -rv '^#' /etc/sudoers /etc/sudoers.d/  # NOPASSWD, ALL=(ALL) excesivos
sudo passwd -S -a                                # contraseñas vacías o bloqueadas
```

**Cuentas temporales**
```bash
for u in $(awk -F: '$3>=1000 {print $1}' /etc/passwd); do echo "== $u"; sudo chage -l $u; done
last -a | head; lastlog | grep -v Never
```
Busca cuentas de soporte o proveedores sin fecha de expiración ("Account expires: never").

**Servicios y puertos**
```bash
sudo ss -tulpn
systemctl list-units --type=service --state=running
```

**SSH y banner**
```bash
sudo sshd -T | grep -Ei 'permitrootlogin|maxauthtries|passwordauthentication|pubkeyauthentication|banner|allowusers|logingracetime|port'
ls /etc/ssh/sshd_config.d/; cat /etc/issue.net
```

**Llaves criptográficas**
```bash
sudo find / -xdev \( -name 'id_rsa' -o -name 'id_ed25519' -o -name '*.pem' -o -name '*.key' \) 2>/dev/null
sudo ls -la /home/*/.ssh /root/.ssh
```
Una llave privada dentro del servidor es un hallazgo por sí sola.

**Firewall**
```bash
sudo ufw status verbose; sudo iptables -L -n -v; sudo nft list ruleset
```

**Permisos de archivos sensibles**
```bash
sudo find /var/www /etc /home /opt /srv /var/backups -type f -perm -o+r \( -name 'wp-config.php' -o -name '*.sql' -o -name '*.bak' -o -name '*.conf' -o -name 'clientes*' \) -ls 2>/dev/null
sudo find / -xdev -type f -perm -0002 2>/dev/null   # world-writable
ls -l /etc/shadow /etc/sudoers
```

**Almacenamiento**
```bash
lsblk -f; sudo blkid; df -hT; cat /etc/fstab /etc/crypttab 2>/dev/null
sudo cryptsetup isLuks /dev/sdX && echo "LUKS" || echo "SIN LUKS"
```
Si en `lsblk -f` el volumen aparece como `ext4` y no como `crypto_LUKS`, está sin cifrar.

## 2. Controles a aplicar

**Usuarios**
```bash
sudo gpasswd -d usuario sudo            # quitar privilegios innecesarios
sudo chage -E 2026-10-31 proveedor1     # vigencia definida
sudo usermod -L -e 1 usuario_innecesario  # bloquear/expirar
sudo visudo -f /etc/sudoers.d/archivo   # eliminar NOPASSWD: ALL
```

**SSH:** edita `/etc/ssh/sshd_config` (o un archivo en `sshd_config.d/`; revisa que no haya otro que lo sobrescriba):
```
PermitRootLogin no
MaxAuthTries 3
LoginGraceTime 30
PasswordAuthentication no     # solo si ya probaste la llave
PubkeyAuthentication yes
AllowUsers admin1 admin2      # cuentas individuales
Banner /etc/issue.net
```
Banner: `echo "AVISO: Acceso restringido a personal autorizado. Toda actividad es monitoreada." | sudo tee /etc/issue.net`

**Llaves:** genera el par en **cliente-examen**, no en el servidor.
```bash
# en cliente-examen
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519
ssh-copy-id usuario@192.168.50.10
# en el servidor
chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys
sudo shred -u /ruta/llave_privada_encontrada   # eliminar la privada del servidor
```
Valida con `sudo sshd -t` y recarga con `sudo systemctl reload ssh`. **Mantén una sesión abierta** mientras pruebas desde otra, para no quedarte fuera.

**Firewall (UFW):** permite SSH antes de activar.
```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.50.20 to any port 22 proto tcp
sudo ufw allow 80,443/tcp      # solo los que el servicio realmente use
sudo ufw enable
```

**Permisos**
```bash
sudo chown root:www-data /var/www/html/wp-config.php
sudo chmod 640 /var/www/html/wp-config.php
sudo chmod o-rwx /ruta/respaldos /ruta/clientes.txt
```
No borres ni dañes `clientes.txt`: solo restringe permisos (por ejemplo `640` con el propietario y grupo adecuados).

## 3. Verificación (positiva y negativa, desde cliente-examen)

| Control | Prueba positiva | Prueba negativa |
|---|---|---|
| Root SSH | `ssh admin1@192.168.50.10` funciona | `ssh root@192.168.50.10` → Permission denied |
| MaxAuthTries | Login con llave correcto | Forzar contraseña incorrecta: `ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no usuario@...` → se corta tras 3 intentos |
| Banner | Se muestra antes del login | — |
| Firewall | `curl -I http://192.168.50.10` responde | `nmap -Pn -p- 192.168.50.10` solo muestra puertos permitidos; `nc -zv 192.168.50.10 <puerto cerrado>` falla |
| Cuenta temporal | Cuenta vigente accede | Cuenta expirada/bloqueada es rechazada |
| Permisos | `www-data` lee `wp-config.php` | Usuario sin privilegios: `cat` → Permission denied |

Para cada una, pon "antes" y "después" y explica qué demuestra.

## 4. Análisis del almacenamiento (sin convertir)

Incluye estos cinco puntos:
- **Situación:** el volumen (ej. `/dev/sdb`) no es `crypto_LUKS` y `clientes.txt` se lee en claro.
- **Riesgo:** robo del disco, snapshot o copia de la VM, o acceso offline exponen los datos de clientes (confidencialidad).
- **Tecnología:** LUKS2 con `cryptsetup` (AES-XTS), con llave o passphrase robusta, y respaldo del header.
- **Procedimiento que aplicarías:** respaldar los datos, luego `cryptsetup luksFormat`, `luksOpen`, `mkfs.ext4`, montar y restaurar, y configurar `/etc/crypttab` y `/etc/fstab`.
- **Comprobación:** `cryptsetup isLuks` devuelve 0, `cryptsetup luksDump` muestra el cifrado, `lsblk -f` muestra `crypto_LUKS` con un mapeo `crypt`, y con el volumen cerrado no se pueden leer los datos.
- **Riesgo residual:** con el volumen desbloqueado, root, un proceso comprometido, malware o un atacante con sesión activa pueden leer los datos, y las llaves están en memoria. Cifrar el disco no protege contra acceso lógico ni contra credenciales robadas.

## 5. Estructura del reporte

Tabla con columnas: **Hallazgo | Evidencia inicial | Riesgo e impacto (C/I/D) | Control | Evidencia final**. Ejemplo:

| Hallazgo | Evidencia inicial | Riesgo e impacto | Control | Evidencia final |
|---|---|---|---|---|
| Root permitido por SSH | `sshd -T` muestra `permitrootlogin yes` + captura de login root exitoso | Un ataque de fuerza bruta contra una cuenta conocida da control total. Afecta C, I y D | `PermitRootLogin no`, recarga de sshd | `sshd -T` con `no` + login root denegado desde el cliente |

Después van los apartados de **Protección del almacenamiento** y **Conclusión**.

**Conclusión:** normalmente el mayor peligro es la combinación de privilegios excesivos con acceso remoto débil (root por SSH, contraseñas, llaves expuestas), porque un solo compromiso da control total. Justifícalo con lo que encuentres. Como riesgo residual puedes mencionar el robo de credenciales o llaves del propietario, el error humano, vulnerabilidades en WordPress o sus plugins, y los datos en claro mientras el volumen está desbloqueado.
